# Отчёт этапа 2

Номенклатура, единицы и выдача кодов базой. Миграции на боевой Supabase не применялись.

## Сделано

- Миграции `supabase/migrations/` по порядку имени: таблицы из модели, enum ролей и статусов, индексы, внешние ключи, `updated_at`.
- Код единицы выдаёт `BEFORE INSERT` через `INSERT ... ON CONFLICT DO UPDATE ... RETURNING`. Вид `ПРЕФИКС-001`, после 999 без обрезки (`ПРЕФИКС-1000`). Значение с клиента игнорируется. `code` и `nomenclature_id` после создания не меняются. Счётчик не уменьшается. `DELETE` единицы запрещён.
- Смена места при любом статусе пишет `movements`, смена статуса — `status_changes`. Автор — `auth.uid()`. Комментарий передают `move_equipment` и `change_equipment_status`. При создании единицы есть начальные строки истории.
- Поверка и даты поверки только у номенклатуры с флагом. Вставка поверки обновляет даты на единице по самой поздней записи.
- Дерево мест без циклов. `location_full_path` и `effective_responsible_employee_id`, представление `locations_with_path`.
- Профиль создаётся триггером на `auth.users` с ролью `viewer`. Отдельная миграция добивает старых пользователей и ставит `admin` для `kb09062001@gmail.com`, если такой пользователь есть. Свою роль сменить нельзя.
- RLS: anon пустой, чтение у активных, единицы и журналы пишут editor и admin, справочники и профили — admin. `public.current_role()` — security definer с `search_path`.
- `supabase/seed.sql` только для локальной разработки, в миграции не входит.
- Фронтенд: типы в `frontend/src/types/database.ts`, типизированный клиент, разделы «Номенклатура» и «Единицы», карточка `/units/:code`. Кнопки правки скрыты по роли из `profiles`. Интерфейс на русском.
- В журнал решений добавлены договорённости про облако и Android: разработка на тестовых данных, переезд на self-hosted, Capacitor на этапе 5, APK на этапе 7.

Коды статусов взяты из журнала решений этапа 1: `in_work`, `on_verification`, `in_repair`, `written_off`, `reserve`. В формулировке этапа 2 были другие латинские имена; расхождение записано ниже.

`./supabase/tests/run.sh` на локальном Postgres 16:

- префикс нормализуется и отклоняется вне `A–Z0–9` длиной 2–8;
- код клиента игнорируется, номера идут по порядку и не переиспользуются после списания;
- параллельные 20 вставок дают `RACE-001` … `RACE-020` без дублей;
- неудачная вставка не занимает номер;
- вокруг 1000 формат `PAD-999` и `PAD-1000`;
- счётчики разных префиксов независимы, уменьшить счётчик нельзя;
- удаление единицы и истории запрещено;

- история пишется при создании, смене места и статуса, комментарий RPC сохраняется, перемещение списанной единицы проходит;

- поверка без флага запрещена, даты берутся из более поздней записи;

## Спорные моменты

- Латинские коды статусов оставлены как в `docs/decisions.md` (`in_work`, `on_verification`, `in_repair`), а не `in_use` / `verification` / `repair` из текста задачи. Подписи на экране русские.
- Префикс дополнительно ограничен 2–8 символами `A–Z0–9`. В журнале этапа 1 была только латиница в верхнем регистре. До появления единиц префикс ещё можно переименовать, вместе со счётчиком.
- Строки истории нельзя удалить, и у них нельзя переписать место, статус, время и автора. Комментарий поправить можно. Это ужесточение формулировки «история сохраняется». Прямая вставка в журналы у редактора по RLS остаётся, но автор всегда текущий пользователь.
- Даты поверки на единице берутся из записи с максимальным `verified_at`, а не слепо из только что вставленной строки. Более старая запись, добавленная позже, не затирает свежую дату.
- `supabase gen types` не запускался: в среде нет Docker и CLI Supabase. Типы в `frontend/src/types/database.ts` написаны по фактической схеме и проверены `tsc`.
